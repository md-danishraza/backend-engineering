The 5-Step Multipart Upload Lifecycle

Deep dive into each technical phase of distributed chunked uploads

1
Step 1: Session Initiation

CreateMultipartUpload Handshake

POST /file.mp4?uploads

The client requests an upload session from the backend API. The backend contacts AWS S3 with the target bucket, object key, metadata, and ACL. S3 generates and returns a unique, cryptographically random UploadId. This ID acts as the global transaction coordinator key for all future parts.

Input Parameters: Bucket: "media-vault", Key: "videos/drone-4k.mp4", ContentType: "video/mp4"
Storage Response: Returns UploadId: "VXBsb2FkIElEIGV4YW1wbGU..."
Key Concept: No storage blocks are allocated yet. S3 creates an internal staging manifest tracking incoming parts.
2
Step 2: Client-side Slicing

Zero-Copy Binary Chunking via Blob.slice()

Browser Web API

Reading an entire 10 GB file into JavaScript memory would crash the browser tab with an Out of Memory (OOM) exception. Instead, modern browsers use the zero-copy File.prototype.slice(startByte, endByte) pointer. Chunks are extracted as lightweight Blob references only when a worker thread is ready to stream the bytes.

Byte Offsets: start = (partNumber - 1) * chunkSize, end = Math.min(file.size, start + chunkSize)
S3 Minimum Rule: Every part except the last part must be at least 5 MB. The maximum part size is 5 GB.
Part Indexing: S3 part numbers are 1-indexed (ranging strictly from 1 to 10,000).
3
Step 3: Security & Presigning

Presigned Direct-to-Cloud PUT URLs

AWS Signature Version 4 (SigV4)

Never embed AWS IAM credentials (Access Key & Secret Key) inside frontend client code! Instead, the client requests temporary, cryptographically signed URLs from your backend. Each presigned URL grants write permission only for a specific partNumber and uploadId for a short expiration window (e.g. 15 minutes).

URL Signature: https://bucket.s3.amazonaws.com/key?partNumber=2&uploadId=xyz&X-Amz-Signature=...
Architectural Win: Chunks upload directly from client browser to S3. Your Node.js backend handles 0 GB of file proxy traffic!
4
Step 4: Concurrent Upload & ETags

Parallel Transfer, Checksumming & Auto-Retry

PUT /key?partNumber=N&uploadId=...

Client workers spawn multiple concurrent HTTP PUT streams (typically 3 to 6 concurrent connections to avoid TCP contention). When a part successfully lands in S3, S3 computes its MD5 checksum and returns it in the ETag response header. The client stores each { PartNumber, ETag } in memory and IndexedDB. If any chunk fails (network drop, timeout), only that individual chunk is retried with exponential backoff!

Response Header: ETag: "1b2cf535f27731c974343645a3985328"
Integrity Verification: Client can provide Content-MD5 or x-amz-checksum-sha256 headers so S3 rejects corrupted packets.
Fault Isolation: Failure rate of 1 chunk out of 200 causes a 0.5% re-upload, rather than a 100% restart of the entire file.
5
Step 5: Assembly & Completion

CompleteMultipartUpload & Compound ETag

POST /file.mp4?uploadId=...

Once all chunks have succeeded, the client sends a completion manifest containing the list of all part numbers and their respective ETags, sorted in ascending order. S3 verifies all parts exist, stitches the chunk blocks internally into a single coherent object, and generates a final compound ETag.

XML Manifest: <CompleteMultipartUpload><Part><PartNumber>1</PartNumber><ETag>"hash1"</ETag></Part>...</CompleteMultipartUpload>
Compound ETag Suffix: Notice how S3 multipart objects have ETags like "c4ca4238a0b923820dcc509a6f75849b-24"! The -24 indicates the object was assembled from 24 parts.
Internal Storage Assembly: Modern cloud file systems do not copy bytes around; they stitch internal inode/block pointers in milliseconds!

Production Code Implementations

Real-world implementations in Browser JavaScript, Node.js AWS SDK v3, and REST wire calls

// 1. CLIENT-SIDE MULTIPART UPLOADER (Modern Browser ES6+)
async function uploadFileInMultipart(file, concurrency = 4) {
  const CHUNK_SIZE = 10 * 1024 * 1024; // 10 MB per part (min 5MB)
  const totalParts = Math.ceil(file.size / CHUNK_SIZE);
  console.log(`Starting upload: ${file.name} (${file.size} bytes) in ${totalParts} chunks`);

  // Step 1: Request upload session initiation from your backend
  const { uploadId, key } = await fetch('/api/upload/initiate', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ fileName: file.name, fileSize: file.size, mimeType: file.type })
  }).then(res => res.json());

  // Step 2: Prepare queue of chunks
  const partsQueue = Array.from({ length: totalParts }, (_, i) => {
    const partNumber = i + 1;
    const start = i * CHUNK_SIZE;
    const end = Math.min(file.size, start + CHUNK_SIZE);
    const chunkBlob = file.slice(start, end); // Zero-copy slicing!
    return { partNumber, chunkBlob };
  });

  const completedParts = []; // Will collect { PartNumber, ETag }

  // Step 3: Concurrent Worker Pool for Uploads
  async function uploadWorker() {
    while (partsQueue.length > 0) {
      const { partNumber, chunkBlob } = partsQueue.shift();
      let attempts = 0;
      let uploaded = false;

      while (!uploaded && attempts < 3) {
        try {
          attempts++;
          // Get presigned PUT URL for this specific part from backend
          const { presignedUrl } = await fetch('/api/upload/presign-part', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ uploadId, key, partNumber })
          }).then(res => res.json());

          // Direct HTTP PUT to AWS S3 / Cloud Storage
          const putRes = await fetch(presignedUrl, {
            method: 'PUT',
            body: chunkBlob
          });

          if (!putRes.ok) throw new Error(`HTTP ${putRes.status}`);

          // Extract ETag header from S3 (ensure S3 CORS exposes ETag!)
          const rawETag = putRes.headers.get('ETag');
          const eTag = rawETag.replace(/"/g, ''); // strip quotes

          completedParts.push({ PartNumber: partNumber, ETag: eTag });
          uploaded = true;
          console.log(`Part #${partNumber} uploaded successfully. ETag: ${eTag}`);
        } catch (err) {
          console.warn(`Part #${partNumber} attempt ${attempts} failed:`, err);
          if (attempts >= 3) throw new Error(`Part #${partNumber} failed permanently.`);
          await new Promise(r => setTimeout(r, 1000 * Math.pow(2, attempts))); // Exponential backoff
        }
      }
    }
  }

  // Run workers concurrently
  const workers = Array.from({ length: Math.min(concurrency, totalParts) }, () => uploadWorker());
  await Promise.all(workers);

  // Step 4: Complete Multipart Upload
  // S3 strictly requires parts sorted by PartNumber ascending!
  completedParts.sort((a, b) => a.PartNumber - b.PartNumber);

  const completeRes = await fetch('/api/upload/complete', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ uploadId, key, parts: completedParts })
  }).then(res => res.json());

  console.log('Upload successfully finalized!', completeRes);
  return completeRes;
}
// 2. BACKEND NODE.JS CONTROLLER (AWS SDK v3: @aws-sdk/client-s3)
import { 
  S3Client, 
  CreateMultipartUploadCommand, 
  UploadPartCommand, 
  CompleteMultipartUploadCommand,
  AbortMultipartUploadCommand 
} from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({ region: process.env.AWS_REGION });
const BUCKET = process.env.MEDIA_BUCKET_NAME;

// 1. Initiate Session
export async function initiateUpload(req, res) {
  const { fileName, mimeType } = req.body;
  const key = `uploads/${Date.now()}-${fileName}`;

  const command = new CreateMultipartUploadCommand({
    Bucket: BUCKET,
    Key: key,
    ContentType: mimeType
  });

  const response = await s3.send(command);
  return res.json({ uploadId: response.UploadId, key });
}

// 2. Generate Presigned URL for a Specific Part
export async function getPresignedPartUrl(req, res) {
  const { uploadId, key, partNumber } = req.body;

  const command = new UploadPartCommand({
    Bucket: BUCKET,
    Key: key,
    UploadId: uploadId,
    PartNumber: Number(partNumber)
  });

  // Presign URL valid for 15 minutes (900 seconds)
  const presignedUrl = await getSignedUrl(s3, command, { expiresIn: 900 });
  return res.json({ presignedUrl });
}

// 3. Complete and Stitch Parts
export async function completeUpload(req, res) {
  const { uploadId, key, parts } = req.body;

  const command = new CompleteMultipartUploadCommand({
    Bucket: BUCKET,
    Key: key,
    UploadId: uploadId,
    MultipartUpload: {
      Parts: parts // Array of { PartNumber, ETag } sorted ascending
    }
  });

  const result = await s3.send(command);
  return res.json({
    location: result.Location,
    eTag: result.ETag, // e.g. "c4ca4238a0b923820dcc509a6f75849b-24"
    key: result.Key
  });
}

// 4. Abort / Cancel Session
export async function abortUpload(req, res) {
  const { uploadId, key } = req.body;
  await s3.send(new AbortMultipartUploadCommand({ Bucket: BUCKET, Key: key, UploadId: uploadId }));
  return res.json({ status: "aborted" });
}

Key Architectural Concepts

The subtle edge cases and engineering considerations every senior backend engineer must know

🏷️

What is an S3 Compound ETag?

For standard single-PUT uploads, S3's ETag is the exact hex-encoded MD5 hash of the object. However, for multipart uploads, it is not the MD5 of the whole file!

ETag = MD5( binary_md5(part1) + binary_md5(part2) + ... ) + "-"

Example: "9b2cf535f27731c974343645a3985328-14" indicates the file was composed of 14 parts. Therefore, you cannot verify a multipart object's integrity by simply running md5sum file.mp4 locally without knowing the original chunk sizing!

📏

S3 Chunk Constraints & Limits

  • Minimum Part Size: 5 MB (5,242,880 bytes). S3 will reject parts smaller than 5 MB with an EntityTooSmall error, except for the very last part.
  • Maximum Part Size: 5 GB per individual chunk.
  • Maximum Part Count: 10,000 parts per multipart upload session.
  • Maximum Object Size: 10,000 parts × 5 GB = 50 TB (S3 limit is 5 TB total object size).
Optimal Part Size = Math.max(5MB, Math.ceil(fileSize / 10000))
💸

The Hidden Cost: Orphaned Parts

When an upload is aborted, interrupted, or abandoned midway, the chunks uploaded so far do not appear in standard bucket listings, yet AWS continues to bill you for their storage!

⚠️ Mandatory Production Rule: Always configure an S3 Bucket Lifecycle Rule: AbortIncompleteMultipartUploadAfterDays = 7. This instructs AWS to automatically purge abandoned chunks after 7 days, preventing surprise thousands of dollars in hidden storage charges.
🌐

Direct-to-S3 vs Proxy Architecture

Why not stream chunks through your Node.js/Go server?

  • Server Proxy: If 1,000 users upload 1 GB video files through your API, your servers must ingest 1 TB and egress 1 TB. High bandwidth bills, CPU spikes, and memory buffering.
  • Direct Presigned URLs: The client streams chunks directly to Amazon S3 edge endpoints. Your backend only signs lightweight tokens (a few bytes). Zero bandwidth costs on your servers!
💾

Resumability & Client State Persistence

What happens if the user accidentally closes the browser tab or loses power?

Store the upload session state in browser IndexedDB or localStorage: { fileHash, uploadId, key, completedParts: [{ PartNumber, ETag }] }. When the user reopens the app, check if an unfinished session exists for that file, query S3's ListParts API, and resume uploading only the missing chunk indices!

🔒

CORS & Security Considerations

Because the browser issues direct HTTP PUT requests to AWS S3, proper CORS (Cross-Origin Resource Sharing) headers are required on your S3 bucket.

ExposeHeaders: ["ETag"]
AllowedMethods: ["PUT", "POST", "GET"]
AllowedOrigins: ["https://yourdomain.com"]

Critical detail: If ExposeHeaders: ["ETag"] is omitted in the S3 CORS configuration, the browser's JavaScript will not be able to read the ETag header from the response!
